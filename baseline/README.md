# Исходная распределённая система такси

Этот стенд реализует исходную архитектуру урока `distributed-systems`. Два экземпляра монолита используют одну основную PostgreSQL и копию чтения. Отдельный процесс публикует сохранённые события в Kafka, консьюмер обновляет диспетчерскую сводку, а исполнитель доставляет сохранённые задания уведомлений.

Код HTTP-приложения берётся из _../monolith/src_ при сборке образа. Схема и миграции монолита тоже используются из соседнего каталога. Для этого профиля отдельная миграция добавляет outbox и очередь уведомлений. Каталог первого курса _monolith_ сохраняет прежний запуск и поведение.

## Первый запуск

Нужны Docker с Compose и сеть для первой загрузки образов и зависимостей. Node.js на хосте для запуска приложения не требуется. Из корня репозитория выполните следующие команды.

```bash
cd baseline
make up
```

После готовности стенда создайте поездку. Заголовок задаёт постоянный ключ операции. В учебной базе есть пассажиры и водители с номерами от 1 до 20.

```bash
curl -s http://localhost:8082/trips \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: baseline-trip-1' \
  -d '{"passengerId":1,"pickupAddress":"Лесная, 10","destinationAddress":"Садовая, 5"}'
```

Ответ содержит числовой `id`, статус `searching` и стоимость 149 по тарифу economy. Запрос завершается после сохранения поездки, события и задания уведомления. Прямой вызов уведомлений в этом профиле выключен. Сохранённое поле ответа `notified: false` относится к прямой отправке; результат фоновой доставки читается отдельно.

Если это первый заказ в чистом стенде, его идентификатор равен 1. В остальных запусках замените 1 в следующих URL значением из ответа создания. Через несколько секунд прочитайте поездку, её сводку и подтверждение получателя уведомления.

```bash
curl -s http://localhost:8082/trips/1
curl -s http://localhost:8082/summary/trips/1
curl -s http://localhost:8082/deliveries/1
```

Сводка должна содержать `trip_id: "1"`, статус `searching` и стоимость `"149.00"`. Подтверждение доставки содержит ключ `trip-created/1`. Пока фоновая работа не завершена, последние два запроса могут возвращать HTTP 404. Повтор создания с прежним ключом возвращает прежнюю поездку и не создаёт ещё один набор фоновых заданий.

История пассажира читается с копии. Заголовок `X-Source: replica` позволяет проверить выбранный источник; новая поездка появляется там после доставки изменений PostgreSQL.

```bash
curl -si http://localhost:8082/passengers/1/trips
```

Порт API меняется переменной `WEB_PORT`. `make down` останавливает стенд и сохраняет данные, включая журнал Kafka. `make reset` удаляет контейнеры и тома только текущего проекта Compose, после чего `make up` создаёт исходное состояние.

## Соответствие схеме урока

| Участник на схеме | Сервис Compose | Работа и состояние |
| --- | --- | --- |
| Балансировщик | `nginx` | Направляет запросы двум экземплярам HTTP-приложения |
| Экземпляры приложения А и Б | `app`, `app2` | Запускают одинаковый код монолита в отдельных процессах |
| Основная PostgreSQL | `db` | Хранит поездки, водителей, события outbox и задания уведомлений |
| Копия чтения | `replica` | Получает основные таблицы логической репликацией и обслуживает историю |
| Публикация событий | `publisher` | Читает outbox, ждёт подтверждения Kafka и отмечает публикацию |
| Журнал событий | `kafka` | Сохраняет записи темы taxi-trips с ключом поездки |
| Консьюмер сводки | `consumer` | Применяет события к отдельной модели чтения и сохраняет результат обработки |
| Хранилище сводки | `summary-db` | Хранит по одной актуальной строке на поездку и обработанные идентификаторы событий |
| Чтение сводки | `summary` | Отдаёт сохранённую сводку через `/summary` и `/summary/trips/{id}` |
| Исполнитель уведомлений | `notification-worker` | Читает задания PostgreSQL и повторяет неподтверждённую отправку |
| Внешний сервис уведомлений | `notifications`, `notifications-db` | Имитирует получателя и сохраняет одно подтверждение на ключ операции |

Внутри монолита операции поездок, тарифов и водителей остаются частью одного процесса. Назначение выполняется через `POST /trips/{id}/accept` с телом `{"driverId":1}`. Основная транзакция проверяет доступность водителя; копия чтения и сводка в принятии решения не участвуют.

SQL-триггер _db/pipeline.sql_ добавляет событие при создании и изменении поездки, а задание уведомления при её создании. Триггер работает в транзакции изменения поездки. Поэтому откат создания откатывает обе записи. Этот способ позволяет использовать исходный код монолита без отдельной копии обработчиков.

Публикация и доставка допускают повторы. Консьюмер сохраняет обработанный идентификатор вместе с моделью чтения, затем подтверждает позицию Kafka. Повтор события не меняет предметный результат. Версия события также не позволяет старой записи вернуть сводку к прежнему состоянию. Получатель уведомлений сохраняет ключ и результат независимо от исполнителя. Счётчики `deliveries` у события и `requests` у получателя показывают повторные доставки.

## Остановка консьюмера

Остановите только консьюмер сводки.

```bash
docker compose stop consumer
```

Создайте следующую поездку с новым ключом `baseline-trip-2`. Основной API продолжит сохранять поездки. Сводка прежних поездок доступна, но сводка новой пока возвращает HTTP 404. Запустите консьюмер и проверьте, что новая поездка появилась в сводке.

```bash
docker compose start consumer
```

Аналогично можно остановить `publisher` или `kafka`. При сохранной основной базе новые события останутся в outbox. Возвращение публикации и консьюмера позволит обработать их. Этот опыт проверяет продолжение пути записи и восстановление малой очереди; допустимое продуктом отставание в пять минут отдельно задаётся как требование курса.

## Отказ уведомлений

Включите отказ учебного получателя.

```bash
docker compose exec notifications node baseline/src/request.ts \
  http://localhost:8080/_control POST '{"failRate":1}'
```

Создайте новую поездку с новым ключом. Запрос создания и обновление сводки должны завершиться независимо от отказа отправки. Посмотрите состояние работ в основной базе.

```bash
make inspect
```

Неподтверждённое задание имеет пустое `delivered_at`, число попыток и последнюю ошибку. Уберите отказ и проверьте доставку.

```bash
docker compose exec notifications node baseline/src/request.ts \
  http://localhost:8080/_control POST '{"failRate":0}'
```

После 20 неудачных попыток исполнитель оставляет задание для разбора. После устранения причины команда `make retry ID=1` возобновляет отправку указанного задания. Для опыта с потерянным ответом установите `{"delayMs":1500}` вместо отказа. Получатель сначала сохранит подтверждение, затем задержит ответ дольше бюджета исполнителя 500 мс. Повтор с тем же ключом вернёт прежний результат.

## Переход к следующей стадии

Каталог [distributed](../distributed) показывает дальнейшие решения курса. Данные поездок разделяются по городам, появляется карта размещения, перенос шарда и отдельный платёжный процесс. [Таблица перехода](../distributed/README.md#исходная-схема-и-дальнейшее-развитие) сопоставляет обе стадии и различия их контрактов.

Это самостоятельные учебные профили с отдельными данными. Запуск distributed не переносит созданные здесь поездки автоматически. Механизм переноса внутри distributed работает между его собственными узлами. Исходный профиль нужен для разбора общей базы, событийного контура и частичных отказов; профиль distributed нужен для новых границ данных и координации.

## Проверки и ограничения

Приёмочный прогон требует Node.js 26 и pnpm 12 на хосте. Из каталога _baseline_ с mise выполните следующие команды.

```bash
mise exec -- pnpm install --frozen-lockfile
mise exec -- pnpm check
mise exec -- pnpm test
```

Прогон создаёт отдельный проект Compose `taxi-baseline-check-<pid>`, выбирает свободные порты на localhost, сохраняет журналы в _reports_ и удаляет только свои контейнеры и тома. Проверяются оба экземпляра приложения, репликация, сводка, независимая доставка уведомлений, повторы и восстановление после остановок. Код и Compose первого курса остаются без изменений. [Результаты выполненного прогона](./verification/README.md) сохранены рядом с примером.

В стенде один брокер Kafka и по одному узлу каждого основного хранилища, кроме копии PostgreSQL. Это не конфигурация высокой доступности и не замер производительности. Потеря машины с локальными томами выходит за пределы опыта. Учебный сервис уведомлений сохраняет факт приёма, но не отправляет реальные сообщения пользователям.

Механизм транзакционного триггера описан в [документации PostgreSQL](https://www.postgresql.org/docs/18/trigger-definition.html), а порядок подтверждения позиции в [документации KafkaJS](https://kafka.js.org/docs/consuming).
