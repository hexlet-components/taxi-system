# Распределённый сервис такси

Готовый учебный сервис для третьего курса программы по проектированию систем. Данные поездок разделены по городам, платёжные резервы принадлежат отдельному сервису. Вы запускаете приложение, меняете условия опыта и проверяете сохранённый результат у обоих участников. Писать сервисы самостоятельно не требуется.

## Запуск и результат

Нужны Docker с Compose и доступ к реестрам образов и npm при первой сборке. Основной стенд запускается без Node.js на хосте.

```bash
cd distributed
make up
```

Создайте поездку города 1. UUID в заголовке служит постоянным идентификатором операции. В исходных данных каждый город имеет водителей с номерами от 1 до 20 и версией 1.

```bash
curl -s http://localhost:8081/cities/1/bookings \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 00000000-0000-4000-8000-000000000042' \
  -d '{"driver":1,"driver_version":1,"amount":900}'
```

Ответ содержит идентификатор и состояние `reserving`. Отправитель прочитает сохранённую команду и обратится к платежам. Прочитайте результат ещё раз через секунду.

```bash
curl -s http://localhost:8081/cities/1/bookings/00000000-0000-4000-8000-000000000042
```

Ожидается `confirmed`. Повтор создания с тем же ключом и данными возвращает ту же поездку. Другие сумма или водитель с прежним ключом дают HTTP 409. Попытка назначить занятого водителя другой поездке тоже получает HTTP 409. Для города 2 замените город в URL и UUID в заголовке. Водитель 1 города 2 принадлежит другому шарду.

Посмотрите резерв у его владельца. Вызов выполняется внутри сети Compose.

```bash
docker compose exec gateway node src/request.ts \
  http://payments:8080/reservations/1-00000000-0000-4000-8000-000000000042
```

Ожидаются сумма 900 и состояние `reserved`. Учебный платёжный участник сохраняет резерв, но не моделирует баланс банковского счёта и взаимодействие с платёжной системой.

Порт API меняется через `WEB_PORT`. `make down` останавливает стенд с сохранением данных. `make reset` удаляет данные только текущего проекта Compose. После сброса `make up` создаёт исходную карту и водителей заново.

## Устройство и владение данными

| Участник | Данные и обязанность |
| --- | --- |
| `gateway` | Читает карту и направляет HTTP-запрос на владельца города, передаёт версию размещения |
| `coordinator` | Хранит карту, аренду контроллера и этапы переносов в PostgreSQL |
| `node-a`, `db-a` | Изначально хранят поездки и водителей города 1 |
| `node-b`, `db-b` | Изначально хранят поездки и водителей города 2, могут принять город 1 |
| `worker` | Доставляет команды из outbox по HTTP и сохраняет результаты у владельца поездки |
| `payments`, `payments-db` | Хранят резерв и окончательное освобождение по ключу операции |

Каждый сервис приложения работает отдельным процессом. Сервис поездок имеет доступ только к своей базе, платёжный сервис только к платёжной. Отправитель читает команды и записывает ответы через API владельца. Контроллер переноса подключается к координатору и вызывает административные методы узлов.

В этом малом примере один город соответствует одному логическому шарду. Совместное размещение двух городов на `node-b` не объединяет их операции в одну транзакцию приложения. Основные таблицы содержат город в ключах и внешних ключах.

Создание поездки блокирует строку водителя, проверяет его версию, сохраняет поездку и команду `reserve` одной транзакцией. Уникальный частичный индекс запрещает две незавершённые поездки одного водителя. Блокировка строки управления шарда сопровождает локальную операцию до COMMIT, поэтому остановка шарда ждёт начатые операции и запрещает последующие.

## Платёжный вызов и сохраняемый процесс

Состояния `reserving`, `confirmed`, `compensating`, `cancelled` и `blocked` хранятся в базе поездок. Состояние `completed` обозначает выполненную поездку и освобождает водителя для следующего назначения. Кнопка завершения здесь не моделирует списание денег, а отмена выполненной поездки требует отдельного процесса возврата и получает отказ.

Строка outbox создаётся в транзакции предметного изменения. Отправитель повторяет команду с постоянным ключом. Платёжный участник фиксирует ответ вместе с изменением резерва. Потеря ответа допускает повторную доставку. Подтверждение поездки и принятие отмены блокируют одну строку процесса, поэтому поздний ответ резервирования не отменяет сохранённое намерение клиента.

Команда `release` сохраняет окончательное состояние `released`, даже если резерв ещё не пришёл. Последующее резервирование с тем же ключом возвращает `released` и не открывает резерв. Эту запись необходимо сохранять столько, сколько возможна повторная доставка.

У отправителя бюджет одного платёжного вызова 250 мс, одновременно идут максимум четыре вызова. Бюджет действует и на чтение тела ответа. Платёжный участник ограничивает число одновременно обрабатываемых команд восемью. После 20 неудачных ответов команда остаётся сохранённой, процесс получает `blocked`. Метод `retry` возобновляет незавершённую обязанность после устранения причины.

### Потерянный ответ

Задержите ответ резервирования на 1500 мс. Задержка начинается после COMMIT платежей, поэтому таймаут клиента не отменяет созданный резерв.

```bash
docker compose exec gateway node src/request.ts \
  http://payments:8080/admin/fault POST \
  '{"action":"reserve","delay_ms":1500}'
```

Создайте следующую поездку со свободным водителем и новым UUID. Проверьте `reserving` у поездок и `reserved` у платежей. После остановки отправителя сохранённая команда остаётся в базе.

```bash
docker compose stop worker
docker compose restart node-a
```

Уберите задержку и запустите отправителя. Он повторит тот же резерв и завершит подтверждение.

```bash
docker compose exec gateway node src/request.ts \
  http://payments:8080/admin/fault POST \
  '{"action":"reserve","delay_ms":0}'
docker compose start worker
```

### Отмена и незавершённая компенсация

Отмените поездку из первого запуска.

```bash
curl -s -X POST \
  http://localhost:8081/cities/1/bookings/00000000-0000-4000-8000-000000000042/cancel \
  -H 'Content-Type: application/json' -d '{}'
```

Сначала возможен `compensating`. Итог `cancelled` означает подтверждённое закрытие резерва. Чтобы увидеть ожидание компенсации, до отмены другой подтверждённой поездки включите отказ `release`.

```bash
docker compose exec gateway node src/request.ts \
  http://payments:8080/admin/fault POST \
  '{"action":"release","unavailable":true}'
```

Пока освобождение получает HTTP 503, поездка не должна сообщать завершённую отмену. Уберите отказ тем же вызовом с `"unavailable":false`. Если процесс уже достиг `blocked`, отправьте `POST` на URL поездки с суффиксом `/retry`. Проверьте итог у обоих владельцев. Настройка отказа находится в памяти платёжного процесса и сбрасывается при его перезапуске.

## Перенос города между узлами

Выполните перенос города 1 с `node-a` на `node-b`.

```bash
make transfer CITY=1 TARGET=node-b
make inspect
```

Карта должна показывать `node-b`, версию 2. Созданные поездки остаются доступны по тому же клиентскому URL. Город 2 продолжает обслуживаться на своей части.

Контроллер сохраняет намерение, получает поколение и активирует его у обоих узлов. Затем останавливает источник, сохраняет снимок водителей, поездок и outbox, устанавливает его на цели и сверяет содержимое. Публикация новой карты выполняется условной записью с прежней версией. Только после публикации целевой узел открывает обслуживание. Источник сохраняет запрет после перезапуска.

Установка одного снимка идемпотентна. Повтор подтверждённой установки сверяет идентификатор и хеш, сохраняя последующие поездки цели. Каждый метод управления проверяет активное поколение в той же транзакции, где меняет локальное состояние. Новое поколение защищает от команд предыдущего держателя после активации у участника.

Для опыта с прерыванием начните с исходной карты после `make reset` и `make up`, затем остановите контроллер после копирования.

```bash
docker compose run --rm --no-deps -e STOP_AFTER=copied tools \
  node src/transfer.ts start 1 node-b
make inspect
```

Команда завершится ошибкой с UUID сохранённого переноса. В этот момент источник уже закрыт, цель ещё не принимает приложение. Скопируйте UUID из ошибки или таблицы и продолжите тот же перенос.

```bash
make resume ID=00000000-0000-4000-8000-000000000099
```

Замените UUID в команде идентификатором своего переноса. Штатный выход команды освобождает аренду. После аварийного завершения процесса преемник ждёт истечения аренды, которая длится 30 секунд по часам координатора. Продление аренды в этом малом контроллере не реализовано. Если она истекла во время работы, повторите `resume` после получения нового поколения.

Проверки автоматически воспроизводят истечение аренды, возврат прежнего контроллера, повтор установки после новой записи и последующий перенос актуальных данных обратно. Единственная PostgreSQL координатора ограничивает доступность карты и управления. Её потеря не компенсируется сохранённым намерением.

## Проверки

Для проверки типов и приёмочных сценариев на хосте нужны Node.js 26 и pnpm 12. Версии объявлены в _../mise.toml_. При наличии mise выполните из этого каталога следующие команды.

```bash
mise exec -- pnpm install --frozen-lockfile
mise exec -- pnpm check
mise exec -- pnpm test
```

Приёмочный прогон создаёт отдельный проект Compose с именем `taxi-check-<pid>`, публикует служебные порты только на `127.0.0.1` со свободными номерами и удаляет только свои контейнеры и тома. Работающий учебный стенд сохраняется. Сценарии останавливают процессы и базы, проверяют HTTP-ответы и сохранённые данные. Вывод TAP называет каждую проверку. Результаты выполненного запуска и исходные истории сохранены в [отчёте проверки](./verification/README.md).

Отдельный опыт [переключения PostgreSQL](./failover/README.md) поднимает Patroni, три участника etcd и HAProxy. Его результаты сохраняются в JSON и проверяются отдельно от журналов процессов.

## Связь с уроками

| Тема курса | Что можно проверить в примере |
| --- | --- |
| Введение | Создание поездки, её состояние и резерв у самостоятельного владельца |
| Что такое распределённая система | Отдельные процессы, базы, сетевые вызовы и частичный отказ участника |
| Шардирование и выбор ключа | Два города, независимое назначение водителей и локальные ограничения |
| Маршрутизация и размещение | Карта города, адрес узла и версия, размещение двух частей на одном узле |
| Согласованность и гарантии | Два конкурентных назначения, повтор операции и постоянный результат |
| Передача полномочий | Аренда координатора, новое поколение и отказ поздней команды |
| Перенос данных | Снимок, сверка, публикация, продолжение прерванных этапов |
| Переключение и консенсус | Отдельный опыт Patroni, etcd, потери связи управления и старого писателя |
| Конкурентная запись | Один владелец записи и отказ устаревшей версии водителя; active-active не реализован |
| Границы сервисов | Раздельное хранение поездок и платёжных резервов, HTTP-контракт |
| Вызовы между сервисами | Стабильное имя Compose DNS, бюджет, предел параллелизма и медленный ответ |
| Распределённый процесс | Локальный outbox, сохранённая обязанность, повтор и компенсация |
| Конкурирующие процессы | Отмена во время резервирования и окончательное закрытие до поздней команды |
| Зоны доступности | Остановка одного владельца и продолжение работы другого; облачный отказ зоны не воспроизводится |
| Проверка системы | Автоматические проверки инвариантов, состояния владельцев и границ вывода |

Стенд проверяет малые истории. Он не подтверждает расчётную пропускную способность, доступность облачной зоны, безопасность production-развёртывания или сохранность локальных томов при потере машины. Административные методы и учебные пароли предназначены для изолированного локального опыта. В основном стенде нет репликации PostgreSQL. Отдельный опыт переключения не подключён к сервисам бронирования.

Механизм блокировок и конкурентной условной записи описан в [документации PostgreSQL](https://www.postgresql.org/docs/18/transaction-iso.html). Запуск TypeScript без сборки использует [поддержку Node.js](https://nodejs.org/api/typescript.html), а проверка типов выполняется отдельной командой `pnpm check`.
